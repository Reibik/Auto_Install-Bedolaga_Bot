# Архитектура и модель безопасности

## Границы ответственности

Manager устанавливает и обслуживает Bot, Cabinet, PostgreSQL, Redis и Caddy. Remnawave Panel не входит в стек: Bot обращается к ней по HTTPS API с ключом, введённым владельцем сервера.

Manager владеет следующими путями:

- `/usr/local/lib/bedolaga-manager`;
- `/usr/local/bin/bedolaga`;
- `/opt/bedolaga`;
- `/etc/bedolaga`;
- `/var/lib/bedolaga`;
- `bedolaga-backup.service` и `bedolaga-backup.timer`.

Он не удаляет чужие контейнеры, images, networks или volumes и не выполняет глобальный `docker system prune`.

## Сети

`backend` помечена как `internal` и содержит PostgreSQL, Redis и Bot. `edge` содержит Caddy, Cabinet и Bot. Только Caddy имеет опубликованные порты.

Разделение не позволяет обращаться к базам напрямую снаружи и не требует host-порта 8080 для Bot или 3020 для Cabinet.

## Секреты

Секреты хранятся в `/etc/bedolaga/*.env` с режимом `600`. Manager не печатает содержимое этих файлов в обычных командах и не включает токены в URL диагностики.

Файлы бэкапа также имеют режим `600`, но содержат секреты и дамп базы. Их следует дополнительно копировать в зашифрованное внешнее хранилище.

## Модель обновления

Исходники upstream считаются управляемыми и должны оставаться чистыми. Пользовательская конфигурация хранится за пределами checkout, поэтому обновление не требует перезаписи `.env` внутри Git-репозиториев.

Перед обновлением сохраняются commit и резервная копия. Новый commit сначала собирается, затем запускается. При провале health checks Manager возвращает исходники и образы приложения. Автоматический rollback базы намеренно не выполняется, чтобы не потерять записи, появившиеся после запуска новой версии.

## Восстановление

Перед restore создаётся emergency-бэкап. Архив проверяется по SHA-256, а его список файлов — на абсолютные пути и `..`. Затем останавливаются прикладные сервисы, восстанавливаются конфигурация, постоянные файлы и PostgreSQL dump.
